# アカウントと同期の設計（段階6）

これは**設計の検討書**です。まだ実装しません。決めるべきことを整理し、私の推奨を示します。

---

## 1. 何のために作るか

目的は2つあり、**重さがまったく違います**。

| 目的 | 中身 | 重さ |
| --- | --- | --- |
| **A. 失わないこと** | 端末が壊れても、ブラウザのデータを消しても、問題が残る | 軽い |
| **B. 複数の端末で使うこと** | PCで作ってiPadで解く。両方の編集が合流する | 重い |

**Aだけなら、いまの4分の1の手間で作れます。** そして、実際に起きた事故（別端末で15問を失った件）は
**Aだけで防げます**。Bは「あったら便利」ですが、無くても困りません。

> **推奨：Aを先に出し、Bは反応を見てから。**
> Bの本体は「2つの端末で別々に編集したとき、どちらを残すか」という難問です。
> 利用者が50人の段階で、そこに時間を使う理由は薄いと考えます。

---

## 2. 段階6a：サーバーに預けて、戻せるようにする

### できること

- メールアドレスでログインする
- ボタン1つで、いまの問題と学習記録をサーバーに預ける
- 別の端末（または消してしまった端末）で、預けたものを取り戻す
- **過去7日分**を保持し、いつの状態にでも戻せる

### できないこと（あえて）

- 自動では同期しません。**預ける・取り戻す**を利用者が押します
- 同時に編集したときの合流はしません（それは6b）

### なぜこれで足りるか

いまも「書き出す・読み込む」でファイルを渡せば同じことができます。6aはそれを
**ファイルを扱わずに、押すだけで**できるようにするものです。ファイル操作は、
スマホでは特につまずきます。

## 3. 使う道具と費用

すでに Cloudflare に載っているので、そのまま延長できます。

| 用途 | 使うもの | 無料枠 | 50〜200人での見込み |
| --- | --- | --- | --- |
| 受け口 | Cloudflare Workers | 10万リクエスト/日 | **十分**（1人1日10回でも2,000回） |
| 保存 | Cloudflare D1（SQLite） | 5GB | **十分**（1人5MBでも200人で1GB） |
| メール送信 | Resend | 3,000通/月 | **十分**（ログイン1回＝1通） |

**月額の見込み：0円。** 予算3000円の範囲に十分収まります。

> メール送信だけは Cloudflare に機能がないため、外部サービスが要ります。
> いま `support@quiz-make.com` は Cloudflare Email Routing で**受信のみ**設定済みです。
> 送信するには、同じドメインに送信用の DNS 設定（SPF / DKIM）を足します。
> **受信の設定は壊しません**が、設定を触るので事前にお知らせします。

## 4. ログインのしかた（メールOTP）

パスワードは作りません。**覚えるものを増やさない**ためです。

1. メールアドレスを入力
2. 届いた**6桁の数字**を入力（有効期限10分）
3. その端末に鍵（トークン）が保存され、次回から入力不要

### 守りの設計

| 攻撃 | 対策 |
| --- | --- |
| 数字の総当たり | **5回間違えたらその要求を無効化**し、新しい数字を要求させる |
| 大量の送信要求 | 同じアドレス・同じIPからは**1分に1通、1日20通**まで |
| メールを覗かれた | 有効期限10分。使ったら即座に無効 |
| 端末を盗まれた | 設定から「他の端末をすべてログアウト」できるようにする |

### パスキー

任意で足せるようにしますが、**最初は作りません**。メールが使えるなら十分で、
実装と検証の量に見合わないためです。

## 5. 端末は3台まで

4台目でログインしたら、**いちばん古い端末を外す**か聞きます。黙って外しません。

> 3台に絞るのは、費用ではなく**アカウントの貸し借りを防ぐ**ためです。
> 将来の有料機能を考えると、ここは最初から入れておくほうが後で揉めません。

---

## 6. 預けたものをどう保つか（ここが要）

事故を繰り返さないために、**上書きの前に必ず残します**。

- 預けるたびに、その時点の内容を1つのまとまりとして保存する
- **過去7日分**を保持（1日1つ、最大7つ）。それより古いものは自動で消す
- 「取り戻す」画面では、**日付を選んで戻せる**ようにする

```
8/21 22:10  15問・3グループ   ← いま預けているもの
8/20 09:33  15問・3グループ
8/19 21:02  12問・2グループ   ← ここに戻すこともできる
```

> 今回の事故では「書き出したファイルに問題が入っていなかった」ことが致命傷でした。
> **預けたものが本当に戻せるか**は、実装より先に検証の仕組みを作ります
> （預ける→消す→戻す、を自動で通す試験）。

## 7. プライバシーの扱い

**メールアドレスと問題データをお預かりする**ので、いまの約束が変わります。

現在のポリシー第7項に「アカウント機能：メールアドレスと問題データをお預かりする形になります」と
**予告済み**です。実装と同時に改定します。

| いま | 6a のあと |
| --- | --- |
| 端末の中だけに保存 | **預けたときだけ**サーバーにも保存 |
| 提供できる情報がない | メールアドレスと、預けられた問題を保持する |
| 削除は利用者の端末操作 | **退会ですべて消す**導線が必要（法的にも実務的にも必須） |

- ログインは**任意**。使わない人はこれまでどおり、端末の中だけで完結します
- 「預ける」を押すまで、サーバーには何も送りません

## 8. 無料にするか、有料にするか

事業計画では段階8で課金（月300円／買切1000円）、画像アップロードは有料機能としています。
同期の扱いは**まだ決めていません**。

| 案 | 内容 | 考え |
| --- | --- | --- |
| **無料**（推奨） | 誰でも預けられる | 事故を防ぐ機能を有料にすると、失った人が「お金を払っていれば」と感じる。評判に直結する |
| 一部無料 | 直近1件だけ無料、7日分の履歴は有料 | 線引きが説明しづらい |
| 有料 | 課金者のみ | 利用者50人の段階では、課金者は数人。作る価値が出ない |

> **推奨は無料**です。費用が0円で回る見込みである以上、ここで課金する理由が弱いと考えます。
> 有料にすべきは、**費用がかかるもの**（画像の保存）です。

## 9. 作る順序と、かかる量

| 手順 | 内容 | 目安 |
| --- | --- | --- |
| 1 | D1 のテーブル設計、Workers の受け口を用意 | 半日 |
| 2 | メール送信（Resend）と DNS 設定 | 半日 |
| 3 | OTP のログインと端末管理 | 1日 |
| 4 | 預ける・取り戻す・7日分の保持 | 1日 |
| 5 | アプリ側の画面（設定の中） | 半日 |
| 6 | 通し試験（預ける→消す→戻す）とポリシー改定 | 半日 |

**合計 4日ほど**（私の作業時間。あなたの確認時間は別）。

6b（自動で双方向に同期）を足すなら、**さらに同じくらいかかり、難しさは段違い**です。

## 10. 決めてほしいこと

1. **6a（預ける・取り戻す）を先に作る**という方針でよいか
2. 同期を**無料**にしてよいか
3. メール送信に **Resend** を使ってよいか（無料枠3,000通/月・独自ドメインのDNS設定が要る）
4. 着手の時期（いま作るか、利用者が増えてからか）

> **4について私の考え**：いま作るのが良いと思います。過去問まとめを配って50人が使い始めると、
> その人たちがデータを失う可能性が出ます。**配る前に受け皿を用意する**ほうが順序として自然です。
